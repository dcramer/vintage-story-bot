# Runtime boundaries

`CLI/agent → controller:42158 → mod:42157 → game inputs/physics`

| Path | Responsibility |
| --- | --- |
| `src/bot.ts` | The Seraph process: loopback controller service, eye loop, installed brain. |
| `src/runtime/` | Core: `bridge.ts` bounded game transport (no retries); `game.ts` RPC client with terrain cursors and scoped control owners; `controller.ts` tool registry, goal lifecycle/exclusion; `navigation/` terrain memory, route planning, exploration, steering (no I/O); schemas, telemetry, reporter, `rpc.ts` controller client. |
| `src/actions/` | One public query/command per file: schema, description, mod wire alias or controller-local handler. |
| `src/goals/` | One public goal per file: schema, description, chat announcement, and its behavior as exported functions other goals compose. |
| `src/support/` | Helpers goals share: `fieldwork.ts` session guard/memory/travel, `task.ts` goal harness, inventory, food, survival priority, threats, block aiming, forming, structures. |
| `src/brain/` | Installable brains ([brain](brain.md)): pure decisions over readings; the bot runs one or none. |
| `src/operator/` | Human/operator UI utilities; never import from gameplay. |
| `mod/Bridge/` | `AiBridgeMod` partials: lifecycle/transport/dispatch, `Sensing`, `Movement`, `Hands`; control hold and life tracker. |
| `mod/Sensors/` | Read-only perception: scene/terrain/context/block-facts/handbook sensors, terrain memory, geometry. |
| `mod/Actuators/` | Input-driven mutations: block actions, inventory transfer/craft, knapping/clay forming. |

- Controller/goals/navigation cannot use screenshots, UI tools, OS focus, or hidden world queries.
- One shared controller, one active goal. A tool marked `concurrent` (chat, map markers, controller memory) runs alongside a goal because it never holds the body. START ≠ completion; observe ids. Restart cancels goals; never auto-resume. Memory is ephemeral.
- Plain async everywhere: a goal is cancelled through its AbortSignal and its own cleanup (control_end, stop) runs before the next goal can hold the inputs; mod deadlines remain independent. Never retry mutations, including frames.

## Design intent

- Simulate a real player through the client's own input pipeline. The mod is a cheaper substitute for driving the GUI, not a bypass: it sets input and control state (mouse buttons, keyboard keys, aim, hotbar) so the game runs its normal callbacks and sends the exact client→server packets a human's mouse and keyboard would. Never write blocks, inventory, or entities directly (`IBlockAccessor.SetBlock`, stack writes): on a client that is prediction the server discards, producing a client-only illusion that vanishes on reconnect. Anything that must persist has to go through a real interaction the server re-validates. Consequence: server-authoritative effects need the same preconditions a player has, including control flags the server learns on their own packets — see [held-item interactions](capabilities.md#held-item-interactions).
- Knowledge on disk: the controller keeps terrain, far-field surface and remembered blocks per world in `VINTAGE_STORY_KNOWLEDGE_DIR` (default `.runtime/knowledge/<identifier>.json`), written atomically at most once a minute while anything changed and on shutdown, loaded when a world's identifier is first observed. Entities and items are not stored. `api.controller.knowledge` reports what is loaded.
- Mod = one player act per wire action, sensed or performed; the rule and its test are in [AGENTS.md](../AGENTS.md#where-behavior-lives). Game owns physics, collision, inventory and server validation. Node owns routes, memory, goals and reaction policies; edit/restart Node without reloading the game.
- Follow [Mineflayer](https://github.com/PrismarineJS/mineflayer/blob/master/docs/api.md)'s state/control separation and [pathfinder](https://github.com/PrismarineJS/mineflayer-pathfinder)'s independent goals, movement policy and outcomes; do not reproduce Minecraft physics or assume its world visibility.
- Goals compose inside one controller-owned goal by calling each other's exported functions. One file per public tool: `src/actions/<name>.ts` (query/command) or `src/goals/<name>.ts` (goal); `src/runtime/registry.ts` discovers them by basename and the CLI and agents share those contracts. `goal_script` accepts a temporary TypeScript-compatible sequence of calls to those discovered goals, parses literal arguments and validates each goal schema; it never evaluates source or exposes Node, network, filesystem, imports, variables or control flow.
- Keep the fast loop local: structured observations → Node decision → bounded input frame. An agent or the brain assigns goals, not individual walking ticks. Perception is approximate visible knowledge, not omniscience; unknown ≠ air, stale ≠ safe.
- Mod owns immediate safety release even if Node hangs. Node decides subsequent reactions; cancellation completes cleanup before another goal runs. Do not auto-resume after damage/death/restart.
- Transport acknowledgement is not gameplay completion. Verify arrival, inventory deltas and life state. Lost replies imply uncertain effects; inspect, never blindly resend.
- Memory must be session-scoped, bounded and invalidatable. Share observations across skills; geometry, resource sightings and failed approaches have different expiry rules. No persistence until world identity/invalidation are defined.
- Prefer this small actions/support/goals split over a second game engine, screenshot loops, or a generic workflow framework.
- With no brain installed, survival runs only inside an assigned task, never as an idle process; a [brain](brain.md) is the one loop that assigns tasks on its own. Food priority pauses navigation on supported ground; control release precedes eating/foraging. Planned pauses preserve parent progress; damage/death/session changes abort the entire task. Thresholds live in `src/support/`.

## Controller RPC

Loopback JSON line: `{action,...args}` → `{ok,...result}` or `{ok:false,error,...}`. One request/connection; controller requests ≤16384 bytes including newline, responses ≤262144 bytes. Mod-wire requests remain ≤1024 bytes. No replay/retry protocol. Mod wire stays private; the CLI and agents use controller actions only.

- `api {}`: schemas, descriptions, execution kind (`query|command|goal`), controller session. No game I/O.
- Goal actions return `{goal:{id,...},controller,...}`; successful START means accepted, not completed. `move_to` also returns legacy `navigation`.
- `goal_script {intent,goalScript}`: one outer goal whose `intent` remains stable in status/telemetry while `goalScript` runs up to 16 sequential `await goals.<name>({...literalArgs});` calls, optionally wrapped in `async () => { ... }`. Steps cannot set `timeoutMs`; stop the outer goal to interrupt the chain. `goal_status.args` retains the submitted pair; fleet telemetry retains the same bounded, validated source for the bot page's Debug view; `progress.subgoal` identifies the current validated goal. Failure or cancellation stops the chain.
- `goal_status {id?}`: latest or retained goal, `args` (parsed request), timestamps (UTC ms), state/progress/result, `active`, controller session. No game I/O or waiting behind game startup. Last 64 completed goals; unknown/evicted/restarted id → `goal_not_found`, never inferred success.
- `active` remains true through finalization. States: `starting|running`, navigation phases, `arrived|blocked|cancelled`; arrival is success only after cleanup. Controller session changes on restart; history is not durable.
- `stop {expectedGoal?}`: guarded cancellation of current/latest goal; no guard = global stop. Reject mismatched id. Separate stop/start deliberately avoids implicit replacement races.
- `events {after?,session?,types?,limit?,waitMs?}` (controller-local): what the controller noticed, as a bounded ring with cursor/session/missed semantics: `sighted` (first confirmation of a sighting), `hurt`, `died`, `alive`, `alert`, `storm` (derived from state deltas), `message` (chat lines polled from the mod's ring), `goal_started`, `goal_finished`. `waitMs` blocks for the next event, served ahead of the request lock. The same log wakes an installed brain. `messages` reads the mod's chat ring directly. The bus reports; it decides nothing.

## Telemetry

Controller → dashboard `POST /ingest` on `127.0.0.1:42159`: one long-lived chunked request of NDJSON lines `{topic,at,data,log}`; `at` is UTC ms, `log:true` appends to the dashboard event log, otherwise only the latest value per topic is kept. Fire-and-forget: bounded queue, coalesced fast topics, 2s reconnect, never awaited by gameplay and never a substitute for `goal_status`/`observe`. Topics: `controller` (info), `state` (observe/sense state), `run` (current life metrics for this controller segment), `map` (visible surface deltas), `frame` (control inputs), `navigation`, `scan`, `goal` (goal view), `action` (other game requests with `ok/error`). Dashboard consumers: `GET /state` snapshot, `GET /events` SSE (`snapshot|update|producers`). Any process may push lines to `/ingest`; the dashboard never sends game or controller requests.

Fleet report (optional, `VINTAGE_STORY_REPORT_URL`): the controller also batches the same topics to the Cloudflare service in [report/](../report/worker.mjs) as `POST /api/report` `{bot:{id,host,pid,version,stream?},at,topics:{[topic]:{at,data}},log:[{topic,at,data}]}` (`stream` is the host's public live-view origin from `VINTAGE_STORY_STREAM_URL`, validated as a bare http(s) origin) with `authorization: Bearer <REPORT_TOKEN>`, one request per `VINTAGE_STORY_REPORT_INTERVAL_MS` (default 10s, floor 1s) and only when a topic or log line changed, body ≤128 KB. [Reporter](../src/runtime/reporter.ts) trims payloads: `frame` and the far-view `map` columns dropped (the fleet page draws the native World Map instead), `scan` to the 12 nearest, `state` to identity/position/vitals/life/condition/hotbar/nearest entities, `goal` fields bounded, `action` log lines only for failures and non-polling requests. Same fire-and-forget rules as the dashboard: a failed batch keeps only the latest topics. Service state: one Durable Object holding the latest topic and last 200 log lines per Seraph and a bounded 540-sample movement trail. Trail samples contain the Seraph's own client-observed position and current goal context; a sample is retained after 0.5 blocks of movement, a goal change, or 60 seconds.

`run` is passive instrumentation over state and inventory replies the controller already receives; it makes no extra game request. One controller segment reports a game life id, observed duration, integrated three-dimensional travel distance, successful movement-sample count, estimated steps (`distance / 0.75 m`), maximum horizontal displacement from that segment's origin, discontinuities, and positive owned-inventory deltas classified by the active goal as gathered, crafted, recovered or other. The fleet Durable Object joins cumulative segment snapshots by game life id idempotently, keeps the original spawn point, sums travel and item gains across controller restarts, freezes a death's duration, and retains the latest 20 lives. `runs.current` and `runs.recent` are returned with each bot; internal per-controller merge snapshots are not exposed.

The dashboard's displayed terrain is not reconstructed from those columns. Vintage Story's `ChunkMapLayer` persists every generated 32×32 RGBA map chunk in the character-local `Maps/<SavegameIdentifier>.db`. On each connection the operator opens the full World Map once while the Seraph is idle, then keeps the minimap HUD active; the game's own minimap follows the player and continuously generates its visible chunks into that database. The operator reads the database without modifying it, decodes `MapPieceDB.Pixels`, hashes chunks, and sends only changes in authenticated batches of at most 18 to `POST /api/native-map`. It also sends the positions already present in `SystemRemotePlayerTracking`, the exact server-filtered player feed used by the native map. It checks every `VINTAGE_STORY_NATIVE_MAP_INTERVAL_MS` (default and floor 5 s) but uploads nothing while no chunk changed and no player moved a block or turned more than 15°. The Durable Object stores chunks by `(bot, world, x, z)`, capped at 16,384 per Seraph. `GET /api/native-map/:world` returns a compact region manifest; `GET /api/native-map/:world/region/:x/:z` returns one 8×8-chunk region. An optional `?bot=` filter preserves per-character exploration, while the unfiltered form merges the newest copy of every coordinate across the fleet.

The Preact SPA renders those pixels in a pannable, zoomable canvas, projects retained trails and objectives directly in world coordinates, and overlays both Seraphs and server-visible players. It draws the whole explored-region footprint at overview scale but fetches exact terrain for only the visible and adjacent regions, capped per viewport, so a growing world does not require one giant screenshot or an unbounded browser download. The fleet view combines Seraphs only when their savegame world identifier matches; bot pages request that Seraph's own long-horizon cache. As a fallback, an explicit `pnpm game map` opens the native World Map while gameplay is idle, reads screen/world calibration through `map_view`, captures the verified Vintage Story window, uploads a ≤90 KB WebP to `POST /api/map-image`, and closes the map. Consumers: routes `/`, `/bots/:id`, `/log`; `GET /api/state`; native map manifest/regions; `GET /api/map-image/:id`; and `GET /api/ws` WebSocket (`snapshot|bot|nativemap|gone`: a report pushes the whole bot record, a native map sync only that Seraph's `nativeMap` summary). Reads are unauthenticated. Bot records and screenshots are evicted when unseen for `RETENTION_HOURS` (default 6); persistent native chunks remain bounded independently and are restored to the view when their Seraph reports again.

## Performance budget

A bot that answers the game late stands still with the keys held, so every part of the loop has a budget and going over is logged (`perf over_budget`: what, value, limit, count and worst since the last line, at most one line per thing per ten seconds; telemetry topic `perf`). Limits live in [budget.ts](../src/runtime/budget.ts): a round trip to the mod (100 ms for sense, observe and control frames, 250 ms otherwise), the mod's own work in one game tick (8 ms) and the longest silence between ticks (250 ms), both measured by the mod and reported as `observe.performance` (`tickMs`, `tickMaxMs`, `frameGapMs`, `frameMs`, worst of the last second), Node's event loop (50 ms at the 99th percentile over five seconds, 200 ms for one stall), one navigator decision (50 ms), one walk-loop iteration (300 ms), the idle eye's cadence (1 s) and starts of one goal kind (6 a minute). The budget reports; nothing in it decides.

## Session log

The bot's durable record of one process, for reading back after the fact: [log.ts](../src/runtime/log.ts). One NDJSON file per start under `.runtime/logs/<bot>/<start>.ndjson` (`VINTAGE_STORY_LOG_DIR`, `VINTAGE_STORY_BOT_ID`), every line `{at,level,scope,event,...fields}` with `at` in ISO milliseconds; lines written for a goal also carry `goal` (id) and `kind`. The file keeps both levels; stderr mirrors `info` lines as `HH:MM:SS.mmm scope event k=v …` (`SERAPH_LOG=debug|info|off`). Writes are never awaited by gameplay and a file that cannot be written is dropped once noted. At startup, before opening its own file, the log removes the bot's files last written more than `VINTAGE_STORY_LOG_KEEP_HOURS` (24) ago, then the oldest until the folder is under `VINTAGE_STORY_LOG_KEEP_MB` (2048), and notes what went as `controller prune`; nothing prunes while a session runs. Telemetry is the live view and stays bounded and lossy; the session log is the record.

| `mod` | `refused` (action, args, error, code, ms) | every mod request but the polling and per-frame ones (action, args, ms) |

## Internal mod protocol

JSON lines on one loopback connection the controller keeps open (`BridgeClient`): every request carries a transport `requestId`, many are in flight at once, and the mod echoes it on each reply so they pair in any order; requests ≤1024 bytes, replies ≤262144. The game thread executes them in arrival order on its tick and answers `expired` when it could not reach one within 3 s; the network thread answers `stalled` on its own when the tick has been silent for 1 s. No replay or retry. Public tools: [tool contracts](../src/actions/) and [goals](../src/goals/).

- `sense {session?,after?,watch?}` → `{state,terrain:{session,reset,cursor,more,clock,cells},surface:{clock,sweeps,columns},sightings:{clock,sightings}}`. `terrain` is the surroundings delta stream (cursor semantics above). `surface` and `sightings` are snapshots of what the eye sees right now, no cursors: the mod keeps only a short view buffer and Node owns memory, so concurrent readers and restarts cannot desynchronize. `surface` rows `[x,z,y,kind,step,code,at,color]`: one sight-verified standing-surface sample per column confirmed in the last 5 s inside the client's real field of view (vertical FOV setting, horizontal from aspect) or the surroundings; `color` is the block's native world-map RGB integer. Radius 64 by day scaled with light down to 12; every column to 16 blocks, even to 32, multiples of four beyond, aligned to world coordinates; `kind` ground|canopy|water|hazard; `sweeps` counts completed passes over the current view so Node can wait for one after turning or changing attention. The eye samples ≤2 ms/64 rays per tick only while a `sense`/`control_step` arrived in the last 5 s, and waits 150 ms after the camera stops turning before sweeping. `sightings` rows `[key,kind,code,x,y,z,how,at,extra]`: kind entity|item|block confirmed within 1 s (entities/items) or 8 s (blocks); how `seen` (line of sight inside the field of view), `near` (surroundings, any direction), `heard` (living entities within 16 blocks, any direction, no line of sight: the one approximation of a sense the client does not model); `extra` `{quantity}` for items, `{facts,access}` for blocks (`facts` `{name,variant,growth}`). `watch` (≤16 code substrings; absent = unchanged) is the eye's attention: matching blocks on or within three cells of each visible surface column are reported as the eye sweeps. Node always includes a default salient set (ore, berry, stick, flint, loose, mushroom, cattail, chest, basket, vessel, fire, torch) and goals add to it. `observe.nearbyEntities` is what is seen or heard this instant (entities only, with `how`, `seenAt`); Node overlays its memory so callers also get entities seen within the last 20 s at their last known point with `visible:false` and `ageMs`. `observe.pickingRange` is the player's reach. The controller's eye loop reads `sense` every 250 ms whether or not a goal is running, so memory is never older than a glance. A null terrain row carries a seventh element, its reason: `changed` (the block was replaced; Node drops the cell) or `forgot` (the eye no longer keeps it in range or fresh; Node keeps what it saw).
- `scan` (explicit read of the current view; goals prefer the sightings feed): surroundings ≤8 blocks, distant 120×90° sight ≤64. `match` filters one code substring; `matches` filters 1–4 alternatives in one volume pass. Both require loaded lines of sight. Pages target ≤12ms/128 rays/32768 cells; native calls can exceed budget. Cursor fixes origin/filter/view, expires after 30s, movement >2 or distant-view rotation >15°. Four cursors, ≤4096 results each. `more` continues enumeration; `incomplete` also flags unloaded/truncated data. Not a world snapshot; revalidate before interaction. Distant object sightings do not imply a traversable route.
- `sightings`, `block_at`, `route`, `goals`, `waypoints` (controller-local): reads of what Node remembers; nothing is asked of the world.
- `terrain {x?,z?,radius?}` (controller-local): merged view of observed surroundings surfaces and seen far view columns, `[x,z,y,kind,source,ageMs]`; drains pending deltas first; absent columns are unknown.
- `control_begin {owner,session,epoch,allowStarvingRecovery?}`: owner 32-hex UUID; observed life session/control epoch; exclusive two-second initial control hold. Every accepted frame renews the ownership heartbeat for two seconds independently of its 1–500ms input duration, so bounded terrain planning does not shrink the next network deadline or extend held keys. The optional recovery scope permits low health only during a controller-authorized food recovery episode; the control hold retains that scope until release.
- `control_frame {owner,sequence,durationMs,yawDegrees,pitchDegrees,forward,jump,sprint?,focus?}`: increasing sequence, duration 1–500ms; atomic inputs/aim. Optional focus `{x,y,z}` only prioritizes a nearby visible sample. Never bypasses lines of sight. Expired/released owners cannot resume.
- `control_step {control_frame fields,session?,after?}`: applies one guarded frame and returns the same state/terrain batch as `sense`. This keeps low-FPS clients to one game-thread request per control hold refresh. A frame received before control hold expiry remains valid if a render tick delays processing; cancelled or late frames cannot revive control.
- `control_end {owner}`: releases only that owner. `stop` releases globally. Manual movement, damage, critical health/oxygen, menu/death/world exit/F8 release control. Primitive actions refused while holding control.
- `target`: native current selection only, including bounded descriptive metadata and cached build-break/use access for selected blocks. Cached access is read-only planning data; the server still validates every action.
- `block_action_begin {id,kind:dig|place,target,slot,item,expectedState,face?,allowStarvingRecovery?}`: caller UUID (32 hex), native selection/inventory/access guards. The optional recovery scope has the same low-health/low-food restriction as control holds. Dig holds normal left-click and advances the vanilla world-interaction system on game ticks as well as rendered frames; place calls the native single-placement path once. Place requires a non-replaceable support and adjacent empty/dry destination; no specialized item-use. Node owns aiming, deadline and completion.
- `block_action_continue {id,sequence}` renews a working dig for ≤2000ms without releasing the button; increasing sequence, expiry terminal. `block_action_status {id}` never renews. Observe includes latest `blockAction`; one record, world-reset scoped. States `working|changed|failed|cancelled`; changed ≠ confirmed success. Only selected operation cell is observed while stationary/in reach/visible, ≤5s after change. Stop/danger release it.
- Block goals verify stable client-observed change (dig → air; place → destination changed + one item consumed in survival). Native prediction may still be corrected later; no server acknowledgement/causality guarantee. Dig drops/pickup are separate; no mutation retries or implicit terrain editing during navigation.
- Controller refreshes ≤500ms frames and renews before route planning; missing process/network/game ticks cannot authorize indefinite input. Frozen game threads enforce expiry on resumption.
